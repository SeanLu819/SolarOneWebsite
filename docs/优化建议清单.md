### ✅ N-22 `pages/seed_data.py` 3192 行 —— **已关闭（2026-09-11，v1.1.6 / v1.5.1）**

> **已彻底解决，且超出原建议。** 原建议是"让 seed_data.py 退化为 JSON 的薄加载器"，实际做法更彻底：**`pages/seed_data.py` 现在是 git-ignored 的纯生成产物，不再进版本库**；`seed_data.json`（已存在，1.5MB）是单一数据源。

**最终形态**：
- `build.sh` 在每次 Vercel build 调 `python -m pages.seed_sync --json`，由 `seed_data.json` 重新生成 `pages/seed_data.py` → 仓库不再重复携带 3192 行数据。
- `pages/seed_sync.py` 的 JSON 模式**只写 `.py`、绝不回写 `.json`**（JSON 是源，不该被构建反向修改）；DB 模式仍双向写（DB 是源）。
- 生成的 `.py` 注入 section 注释（`# ── products (20 items)` 等），保持可读。
- 本地开发新增 `python manage.py regenerate_seed` 命令（fresh clone 后重建 `.py`）；`pages/views/utils._load_seed` 在模块导入失败时回退读 `.json`，双保险。
- CI 在跑测试前先 `seed_sync --json` 重建 `.py`，保证测试环境与生产一致。
- 顺带把 1 个失效的 project cover 路径归一化（`red1-karting-01.webp` → 实际存在的 `red1-karting-1080p-01.webp`）。

### 🟠 N-31 原始记录（2026-09-10 真机复核发现）

**症状**：用户 iPhone 截图 `rt410-series` 页面，主要参数区（4 项）排成 1 列 4 行：
```
260W
POWER
125lm/W
EFFICACY
32500+lm
OUTPUT
18~100°
BEAM ANGLE
```
而桌面端是 2 列 2 行。

**根因**：F8 当初决策错误。原 §15.4 第 6 步记录：「`detail-specs` 在 767px 内收 1 列」理由是「2 列在手机上过挤」（当时 value 1.35rem / label 0.8rem）。**结论：错误**——正确做法是收字号 + gap（1.1rem / 0.7rem / 12px 16px），而不是直接退化成单列。单列在 1 列宽 = 视口宽度时，4 项参数纵向堆叠 4 行，视觉密度比 2×2 反而松散。

**教训**：响应式设计的「退」应该是收字号/边距，而不是退化成单列；前者保持视觉密度，后者破坏与桌面端的一致性。L1 守卫只断言了「有 1 列覆盖」，没断言「必须是 2 列」——F8 决策的反向断言缺失。
