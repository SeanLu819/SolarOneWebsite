# 多语种翻译工作指引

## 1. 范围界定：哪些该译、哪些不该译

### 1.1 三条规则

| 类别 | 规则 | 例子 |
|---|---|---|
| **① 产品型号 / 订购代码** | **一律不译，原样保留** | `FL1M` `FL4M` `RT590FL-S` `RT400HB` `VSP-XXXXW-9M-YP` `FL9M-RGBW` |
| **② 型号 + 通用词组合** | **只译通用词，型号保留** | `M Series` → `Série M` / `M-Serie` / `سلسلة M`（`M` 不动） |
| **③ 通用技术名词 / 界面文案 / 营销文案** | **必须译** | `Input Voltage` `Glare Shield` `Beam Angle` `Warranty` `Accept All` |
| **④ 数字 / 单位 / 国际标准** | **一律不译** | `80~1280W+` `125lm/W` `IP66` `3000K/4000K/5000K` `CRI 80` `500+` `50+` |
| **⑤ 品牌名** | **绝不音译/意译**，六语统一 | `SolarOne`（**不要**写成“索拉万”“SolarUno”等） |

**为什么型号绝不能译**：它是**订购标识**，不是描述性文字。译了以后客户拿着报价单、图纸、招标文件对不上货，属于业务事故。行业惯例是六语全部保留拉丁原样。

> ✅ **现有数据已遵守这条规则**（这是好事，说明沿用即可）：
> - `VSP-XXXXW-9M-YP` 在 fr/de/ar 里**原样保留**
> - `RT410 Series` → `Série RT410` / `RT410-Serie` / `سلسلة RT410`：**只译了 "Series"，型号 `RT410` 保留**
>
> 也就是说 §1.2 的白名单**不需要"改"，只需要"冻结成规范"**，避免以后有人（或机器翻译）把它译掉。

### 1.2 型号白名单（20 个产品名，已从 `seed_data.json` 提取）

**全部纯型号共 17 个 → `name` 字段不需要任何翻译，英文即最终态：**

```
FL1M  FL4M  FL6M  FL9M  FL12M  FL16M  FL9M-RGBW
RT590FL-S  RT390FL-S  RT400HB  RT500HB  RT220UB  RT420FS-S  RT600SL-T  RT820SL-T
VSP-XXXXW-9M-YP  VSP-XXXXW-12M-YP
```

> 其中 `VSP-XXXXW-9M-YP` / `VSP-XXXXW-12M-YP` 已有五语译文（内容就是原样型号本身）。
> 清单 C 段显示「缺译」的 16 个产品里，**15 个正是这些纯型号**（缺的字段就是"不该译的 `name`"）。

**含通用词、需要翻译的只有 3 个（型号部分保留）：**

| 英文 | 需译部分 | 状态 |
|---|---|---|
| `M Series` | `Series` | ✅ 五语已有（`Série M` / `M-Serie` / `سلسلة M`） |
| `RT410 Series` | `Series` | ✅ 五语已有（`Série RT410` / `RT410-Serie`） |
| `Glare Shield for RT410` | `Glare Shield` / `for` | ⬜ 待译，型号 `RT410` 保留 |

> ⚠️ 这条修正了清单里「C 段 **16/20 产品缺译**」的读法：那 16 个里 **15 个缺的是纯型号的 `name`（本就不该译）**
> → `name` 字段**实际只有 1 个产品需要处理**（`Glare Shield for RT410`）。
> 真正需要投入的是产品的 **`description`**（20 个）与 `category`（低优先，见 §3 P3）。

### 1.3 项目名（专有名词）：需要你决策

`docs/i18n_待译清单.md` D 段的 22 个项目，英文标题**绝大多数是机构名/场馆名/地名**，属专有名词：

```
Morgan State University Tennis Courts / Narbonne Arena / Andre Vacheresse Stadium
Beijing Capital International Airport / Hangzhou Asian Games Velodrome
Yingdong Natatorium / North Creek Community Center / Pickle n Par club
```

三种可选策略（**建议 B**）：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 全部保留英文** | 五语都显示英文原名 | 零误译风险；客户可拿原名去 Google 核验背书 | 纯英文标题在 de/ru/ar 市场信任度偏低 |
| **B（建议）专名保留 + 类型词/地名本地化** | `Morgan State University Tennisplätze`（de）/ `Yingdong-Schwimmhalle` / `Pékin` | 兼顾背书与本地可读性 | 需术语表约束，避免同一类型词多种译法 |
| **C 完全本地化** | 机构名也音译 | 最本地化 | ⚠️ 机构名音译后搜不到、也认不出，**不建议** |

**无论选哪个，`description` / `location` / `results` 都应该本地化**（这三项是"讲清做了什么"的内容，不是标识）。

## 2. 技术前提：RTL（阿拉伯语）下的型号必须做双向文本隔离

**现状核查结论**：`templates/base.html:5` 已有 `{% if LANGUAGE_CODE == 'ar' %} dir="rtl"{% endif %}`，
但整个 `templates/` 与 `static/css/base.css` 里**没有任何** `bdi` / `dir="ltr"` / `unicode-bidi` —— **零隔离**。

**为什么这是问题**：拉丁字母串（如 `FL9M-RGBW`、`80~1280W+`、`(Beijing)`）出现在阿拉伯语 RTL 上下文里时，
字符串两端相邻的**中性字符**（`-` `/` `(` `)` `~` `+`）按双向算法可能被重新排序，典型表现：

- 括号跑到错误一侧：`(FL4M` … `)` 
- 连字符跳跃：`RT590FL-S` 显示成 `S-RT590FL`
- 型号与后面的单位/数字位置互换

**建议修法**（任选，成本递增）：

1. 给型号/规格值的渲染位置加 `<bdi>` 或 `dir="ltr"`（精准、改动小）
2. 在 CSS 里给这类元素加 `unicode-bidi: isolate`（统一、一处生效）
3. （兜底）在 seed 数据里给型号串包 `&#8206;`（LRM）——**不推荐**，会污染数据

> ⚠️ **这是"有明确机理的待验证风险"，不是我已目视确认的线上错位。** 项目里已有 Playwright（L2）套件，
> 可以直接在 `/ar/` 页面截图对照确认后再改 —— 建议**先验证再动手**，避免为一个不存在的问题改代码。

## 3. 优先级：先译什么才划算

按「影响用户决策的程度」排，而不是按「英文串多少」排：

### 🔴 P0 — SEO 标题与描述（直接影响自然流量与点击率）

| 来源 | 内容 | 数量 |
|---|---|---|
| E 段 模板硬编码 | 6 个模板的 `<title>` / `<meta description>`（`about` `contact` `home` `news` `products` `projects`） | 24 处 = **12 条唯一文案** |
| B 段 SiteConfig | `meta_title` / `meta_description`（全站默认，`base.html` 的 og/twitter/JSON-LD 都取它） | 2 条 |

**为什么排第一**：五语页面的 `<title>` 现在**全是英文**（已运行时证实），这是搜索引擎与社交分享看到的第一句话。
译完立刻见效，且量小（**约 14 条 × 5 语 = 70 条**）。

> 💡 **注意**：这 24 处其实是 **12 条唯一文案重复两遍**（每个模板的 `<title>` 与 `og:title` 同文，`description` 与 `og:description` 同文）—— 别按 24 条报价。

### 🟠 P1 — 合规与转化文案（A 段 35 条）

| 子类 | 内容 | 为什么优先 |
|---|---|---|
| Cookie 同意条 | `Cookie Usage` / `Essential cookies:` / `Analytics cookies:` / `Reject` / `Accept All`（`base.html`，2026-08-15 引入后从未翻译） | **GDPR 合规**，de 市场尤其敏感；这是法律文本，**不接受机翻** |
| 隐私/数据章节 | `about.html` 的 `Data We Collect` / `Help us understand how visitors interact…` / `Last updated:` | 同上，合规文本 |
| 联系表单提示 | 提交成功/失败提示、校验信息 | 影响询盘转化，用户看不懂就不发了 |

### 🟡 P2 — 品牌文案（B 段剩余 25 个字段）

`hero_title` / `hero_subtitle` / `about_text_1/2` / `about_title` / `contact_title` / `contact_subtitle` / `footer_description` + 各统计标签（`Projects` `Countries` `Energy Save` `warranty` `Years Experience` …）。

> 其中 **6 个（hero/products/projects 的 title+subtitle）已经覆盖**，不用重复做。

### 🟢 P3 — 产品与项目内容（量大、影响中）

| 内容 | 数量 | 备注 |
|---|---|---|
| 产品 `description` | 20 | 从"看得懂"角度值得译；含大量型号，**必须过术语表** |
| 项目 `description` / `location` / `results` | 16 / 16 / 18 缺 | `results`（成效数据）对说服力最有用 |
| 项目 `title` | 16 缺 | 取决于 §1.3 的决策 |
| 产品 `category` | 16 缺 | ⚠️ **最低优先**：`enrich.py:104-106` 有三级兜底（卡片映射 → 分类→侧栏映射 → 才用到这个译文），实测大概率不影响显示 |
| 产品 `name` | 15 缺 | ✅ **不需要做**（纯型号，见 §1.2） |

## 4. 落地通道：每类内容靠什么才能上线

**这是最容易白干的一环** —— 生产是**无状态**的，内容真源是仓库里的 `seed_data.json`，
所以「译了但没进对通道」= 线上永远看不到。核查结果：

| 内容类别 | 译文必须写到哪 | 后台能直接编辑吗？ | 上线方式 |
|---|---|---|---|
| **C/D 段 产品·项目** | `seed_data.json` → `translations.<lang>` | ✅ **能**（`TranslationsWidget`：每语一个输入框 + 自动翻译按钮） | 本地改 → 后台 save（自动导出 seed）→ commit/push |
| **A 段 界面文案** | `locale/<lang>/LC_MESSAGES/django.po` → 编译 `.mo` | ❌ 不能 | 改 `.po` + `polib` 编译 `.mo` → push |
| **A 段 侧栏/规格标签** | `pages/views/i18n.py` 的 `_SIDEBAR_I18N` | ❌ 不能 | 改代码字典 → push |
| **B 段 SiteConfig 27 字段** | ❌ **目前无通道**（无 `translations` 字段、未过 `_t()`） | ❌ 不能 | ⚠️ **需先做代码改动**（见下） |
| **E 段 模板 title/meta** | ❌ 目前**硬编码**，未过任何机制 | ❌ 不能 | ⚠️ 需先包 `{% trans %}` → 转入 A 段通道 |

### 4.1 B 段 / E 段的通道怎么补（P0 的代码改动，建议最小改动方案）

**E 段（12 条唯一文案）**：把模板里的硬编码 `<title>` / `<meta description>` 包成 `{% trans %}`（或 `{% blocktrans %}`），
文案即进入 A 段通道（`.po`/`.mo`）。改动小、立刻生效、每页 title 可独立优化。

**B 段（含 `meta_title`/`meta_description`）**：让 `pages/views/common.py` 对这几个字段也走 `_t()`，
并把五语条目补进 `_SIDEBAR_I18N` —— 沿用**已有的机制②**，**零数据库迁移、零模型改动**，与现有 6 个字段一致。

> 若你希望**以后能在后台直接改五语的 SEO 文案**，则需给 `SiteConfig` 增加 `translations` JSON 字段
> （模型 + 迁移 + admin widget），工作量明显更大。建议**先做上面的最小方案**，把 SEO 修好；
> 「后台可编辑 SEO」作为后续独立需求评估。

### 4.2 一个现实阻塞项（说清楚免得你踩空）

后台「自动翻译」按钮用的是 `deep_translator`（MyMemory），**本机已装（2026-09-17 复核）但质量一般** —— 适合当初稿。
你本地流程要用它，需要先装：

```bash
E:/Python/python3/python.exe -m pip install deep_translator
```

另外两点提醒：
- MyMemory 质量**一般**（尤其俄语/阿拉伯语），适合当"初稿"再人工过一遍，不适合直接发布
- ⚠️ **Cookie / 隐私政策等合规文本不要用机翻**
- 机翻会把内容发到第三方 API；从合规审慎角度，法务/隐私文本建议人工处理

### 4.3 术语表（glossary）—— 建议先冻结再翻译

六语一致性靠的不是"翻译员认真"，而是**术语表**。建议第一批先定这些词的固定译法（英 → 中说明 → 五语）：

`luminaire`（灯具）/ `high bay`（高棚灯）/ `flood light`（泛光灯）/ `modular`（模块化）/ `beam angle`（光束角）/
`glare shield`（防眩罩）/ `efficacy`（光效）/ `warranty`（质保）/ `retrofit`（改造）/ `ordering code`（订购型号）/
`velodrome`（自行车馆）/ `natatorium`（游泳馆）/ `stadium`（体育场）/ `arena`（体育馆）/ `tennis courts`（网球场）/
`energy save`（节能）/ `input voltage`（输入电压）/ `dimming`（调光）/ `finish`（表面处理）/ `LED driver`（驱动电源）

> 已发现的真实反例说明术语表是必要的：项目侧栏 `Airports` 在字典里存的是 `Airports and Ports`，**键名对不上** →
> 长期静默回退英文（N-37 才修）。同类问题靠术语表 + 守卫一起防。

## 5. 译文交付格式（建议：一份 CSV，我写脚本批量导入）

**不要**手改 `seed_data.json` / `.po` / `_SIDEBAR_I18N` 三个地方 —— 易错且无法校验。
建议你（或翻译方）只产出一份表格：

| key | en | fr | es | de | ru | ar | note |
|---|---|---|---|---|---|---|---|
| `po:Accept All` | Accept All | Tout accepter | Aceptar todo | Alle akzeptieren | Принять все | قبول الكل | Cookie 条 |
| `sidebar:Airports` | Airports | Aéroports | Aeropuertos | Flughäfen | Аэропорты | المطارات | 侧栏 |
| `siteconfig.meta_title` | SolarOne — Precision LED Lighting Systems | … | … | … | … | … | P0 SEO |
| `product.fl4m.description` | Truly modular design… | … | … | … | … | … | 型号保留 |
| `project.yingdong-natatorium.title` | Yingdong Natatorium | … | … | … | … | … | 见 §1.3 |
| `template.home.title` | SolarOne — Professional LED Sports Lighting | … | … | … | … | … | 走 gettext |

`key` 命名空间 → 落地位置：

| 前缀 | 写入目标 | 附加动作 |
|---|---|---|
| `po:` | `locale/<lang>/LC_MESSAGES/django.po` | `polib` 编译 `.mo`（本机可做） |
| `sidebar:` | `pages/views/i18n.py` 的 `_SIDEBAR_I18N` | 无 |
| `siteconfig.` | `_SIDEBAR_I18N` 或 SiteConfig 五语（取决于 §4.1 决策） | 无 |
| `product.` / `project.` | `seed_data.json` 的 `translations.<lang>` | `manage.py regenerate_seed` |
| `template.` | 同 `po:`（模板改包 `{% trans %}` 后即入 A 段通道） | 编译 `.mo` |

**导入器（待你确认格式后我实现）会做四件事**：
1. 按前缀分发写入对应位置（幂等，可重复跑）
2. 用 `polib` 编译 `.mo`
3. 重新生成 `pages/seed_data.py` 并跑 `python -m pages.seed_sync --json` 保持同步
4. **跑现有守卫校验**（缺译/回退会被现有测试抓出来）+ 输出「已覆盖/仍缺」报告
