## 2. 问题清单

### 🔴 P0 — 移动端基本不可用（用户实机已确认）

#### P0-1 导航栏溢出：`.nav-links` 在移动端从未隐藏，汉堡被挤出视口

- **现象**：看不到汉堡按钮；只能看到 logo + Home/Products/Projects/News，About 及右侧全部不可见。
- **根因**（代码依据）：
  - `base.css:355-359`：`.nav-links{display:flex}` 为默认值；`@media(min-width:768px){display:flex}` 只重复不隐藏 → **移动端 5 个链接始终显示**，与汉堡按钮并存。
  - `base.css:340-345`：`.nav-inner` 单行 flex、`gap:24px`、无 `flex-wrap`。
  - `base.css:319`：`body{overflow-x:hidden}` → 溢出的内容被静默裁掉，**页面不会出现横向滚动条，用户无法感知溢出**。
  - flex 顺序：汉堡位于容器最右端 → 溢出区域，点不到；移动菜单（mobile-panel）结构完好但入口不可达。
- **估算**：iPhone 14 390px 下，logo + 5 链接 + CTA(≈110px) + 主题(36px) + 语言(≈70px) + 汉堡(44px) + gaps 合计远超 390px。

#### P0-2 移动端无 Contact 入口

- `base.html:66-72`：移动面板仅 5 项（Home/Products/Projects/News/About），**无 Contact**。
- 叠加 P0-1（顶部 nav-cta 溢出不可见）→ 手机端联系入口实际缺失。

#### P0-3 Products / Projects 移动端首屏被分类树占满

- **现象**（用户实机）：进入产品/项目列表页，首屏全是左侧分类导航，下滑很久才见内容。
- **根因**：
  - 折叠规则**存在且生效**（`≤900px` → `sidebar-layout` 折单列，base.css:1650-1658 + 各模板内联 style），手机上确为单列；
  - 但 **DOM 顺序 sidebar 在 content 之前**（products.html:25-61、projects.html:25-49）→ 折叠后分类树整棵排在内容上方；
  - 分类树很长（8 大类 × 每类多系列 × 有的三级子系列），且**无收起机制** → 390px 手机上要滚过整棵树。
- 用户期望：手机上侧栏应收起为"筛选/目录"可折叠入口，且内容应优先展示。

#### P0-4 后台固定字号覆盖响应式 `clamp()`

- 见 1.4。手机上 hero 标题固定 56px（多行堆积、首屏被下压）；副页 section-title 固定 36px 偏大；`--fs-nav` 17px 加剧导航溢出。

### 🟠 P1 — 三端一致性 / 布局问题

#### P1-5 断点体系割裂（768 / 900 / 1024 三套并存）

- 折叠断点 900px 与内容网格断点 768px 不一致：平板竖屏 768–899px 时侧栏已折叠（900 规则）、内容已是 2 列（768 规则）→ 体验割裂；产品页另有 `768–1024px` 的特判（base.css:1659-1663）。

#### P1-6 详情页 901–1024px 双列过挤

- `product_detail.html:846-880` 仅 `≤900px` 才折单列；901–1024px 下 240px 侧栏 + `detail-grid` 1.2fr/1fr + `detail-specs` 2 列（模板 L653-654）→ 主区不足 ~650px 时规格/文字拥挤。

#### P1-7 products-banner 超窄屏裁切

- `products.html:143` 固定 `aspect-ratio:1920/442` + `overflow:hidden`：360px 屏高≈83px、320px 屏高≈73px，banner 文字（label+36px 标题+留白）可能被裁。

#### P1-8 项目卡片标题移动端单行截断

- `.project-card-title`（base.css:1082-1084）`white-space:nowrap; text-overflow:ellipsis`：移动端全宽下也不换行，长项目名被截成"…"，而移动端本有空间换行。

#### P1-9 `.reveal` 区块依赖 JS 才可见

- `base.css:1666-1674` 初始 `opacity:0`，靠 JS 加 `.is-visible`。无 JS / JS 报错时首页预览、about 各区块、news 卡片**整块不可见**（SEO / 无障碍 / 低端机风险）。

#### N-18 项目卡片图片移动端被裁 12px（v1.1.6 复核发现，L2 实测）

#### N-21 侧栏 grid 轨道被 min-content 顶爆（v1.1.7 复核发现，320/360 档整页溢出 44px）

`base.css:1746-1750` → `@media (max-width:900px){ .sidebar-layout{ grid-template-columns: 1fr !important } }`。

**`1fr` 等价于 `minmax(auto, 1fr)`，其最小值取轨道内容的 min-content**，而不是 0。实测 320 档：

```text
div.sidebar-layout   rectW=288  clientW=288  → grid-template-columns: 346.531px  ← 轨道被顶爆
  div.sidebar-content                  rectW=347
    div.projects-grid (flex)           rectW=347
      a.project-card                   rectW=347   ← min-content ≈347px
div.container        rectW=320  scrollW=364        ← 整页溢出 44px
```

- **触发链**：`.project-card` 的 min-content ≈347px → grid 轨道 `1fr` 的 auto 最小值被顶到 346.53px → 轨道（346.53）远大于容器（288）→ 整页横向溢出 44px → 被 `body{overflow-x:hidden}` **静默裁切**（与 P0-1、N-18 同一失效模式）。
- **为何只影响 320/360**：容器可用宽 = 视口 − 32(padding)。320 档仅 288、360 档 328，均 < 347 → 顶爆；≥390 档容器 ≥358 > 347 → 不触发。这也是它长期没暴露的原因。
- **修复（标准解法）**：`grid-template-columns: minmax(0, 1fr) !important;` —— 允许轨道收缩到 0。
- **注意**：`375px` 档容器 = 343 < 347，**理论上也会顶爆**（L2 未覆盖 375 档，建议补档，见 N-12）。

#### N-22 RTL 下移动抽屉仍从右侧滑出（2026-09-10 真机验收发现，P1）

阿拉伯语（`dir="rtl"`）下打开抽屉，面板**依然从右边缘滑入**，与阅读方向相反。  
`base.css:442` 的 `.mobile-panel` 硬编码 `right: 0` + `transform: translateX(100%)`，而 §2 的 RTL 规则表（202-211 行）只覆盖了 `.nav-links / .nav-brand / .nav-actions / .lang-switch-menu` 等，**漏了抽屉本身**。

- **修复**：新增 RTL 镜像规则（`left: 0` + `translateX(-100%)` + 边框/阴影换向 + 关闭按钮移到左侧 + `.panel-actions` 反向）。
- **坑**：`[dir="rtl"] .mobile-panel`（0-2-0）与 `.mobile-panel.open`（0-2-0）**特异性相同**，若写成前者会覆盖后者的 `translateX(0)` 导致抽屉打不开。→ 必须写成 `[dir="rtl"] .mobile-panel:not(.open)`（0-3-0）。
- **验证**：Playwright 实测 `/ar/` 390 档 → `panelLeft: 0` ✅（修复前 130）。

#### N-23 移动端 hero 被裁到只剩约 27%（2026-09-10 真机验收发现，P1）

hero 源图 **1920×1080（16:9）**，但移动 hero 盒子是竖长条。实测：

| 视口              | hero 实际高度 | 容器宽高比 | 图片渲染宽  | **可见宽度占比** |
| --------------- | --------- | ----- | ------ | ---------- |
| iPhone 14 / 390 | **810px** | 0.481 | 1440px | **27.1%**  |
| Android / 360   | **868px** | 0.415 | 1543px | **23.3%**  |

- **根因**：`min-height: 60svh` 完全没起作用——hero 被内容（meta + h1 + lede + 双 CTA + 4 项数据）撑到 810~~868px。`object-fit: cover` 要填满这个高度，必须把 16:9 的图放大到 1440~~1543px 宽，再居中裁到 390 → 只剩中间四分之一。
- **注意**：`object-position: center 42%` 的**纵向分量在此完全无效**（图片高度正好填满容器，纵向无裁切），裁切 100% 发生在横向。
- **已做（缓解）**：`@media (max-width:767px)` 把 `.hero-bg` 压成 `height: 62%` 的图带，并用 `mask-image` 向下淡出融入页面背景。实测可见占比 **27.1% → 43.7%**（Android 23.3% → 37.6%）。用 mask 而非 `::after`，避免被亮色主题的 `::after{background:transparent}` 规则抵消。
- **根治（待做）**：出**竖版 hero 图**（约 900×1200）+ `<picture>` 分档加载。CSS 层已无更好解——16:9 填 0.48 的盒子，只有 `cover`（裁掉 73%）或 `contain`（上下大片留白）两个纯解。

#### N-24 reduced-motion 把轮播整个停掉（2026-09-10 真机验收发现，P0 可访问性）

`templates/base.html` 的轮播 JS 里：

```javascript
if (window.matchMedia && window.matchMedia('(prefers-reduced-motion: reduce)').matches) return;
setInterval(next, interval);
```

开了「减弱动态效果」直接 `return` → **轮播永久停止**，用户永远只看到第 1 张，图 2/3 **不可达**。

- **这是 N-8 自身的副作用**：N-8 为尊重 reduced-motion 关了平滑滚动，顺手在这里也加了一道闸，但**判据错了**——reduced-motion 应只去掉**装饰性动画**（淡入淡出），不该停掉**内容轮播**。停掉反而违反 WCAG 1.1.1（内容不可达）。
- **修复**：删除该 early return，改为在 CSS 的 `prefers-reduced-motion` 块内加 `.hero-slide { transition: none; }` —— 保留切换、去掉淡入淡出。
- **用户环境**：iPhone 14 实机**已开启**「减弱动态效果」，所以该问题 100% 复现。
- **根治（已完成，v1.1.12）**：见 **§13**，已出竖版图 + `<picture>` 分档，N-23 的 62% 图带缓解方案不再需要时可移除。

#### N-25 grid blowout 复发：模板内联 `1fr !important` 反杀 N-21（2026-09-10，P0）

**现象**：用户实机反馈「产品页面的细分页面都没有缩放/重排，进 rt400hb 只能看到很小的一部分」。  
**实测**（`scripts/e2e/visual_review.py`，390×844 视口）：`document.documentElement.scrollWidth = 921`，基准 390 → **整页溢出 531px，手机端只能看到约 42% 的页面**。

**两层原因，缺一不可**：

1. **燃料（内容层）**：`.detail-ordering-table { min-width: 900px }`（9 列）与 `.detail-energy-table` 的 `th { white-space: nowrap }`（实测被撑到 899px）。
2. **传导（布局层）**：`templates/product_detail.html` 的内联 `<style>` 里有  
   `@media (max-width:900px) { .sidebar-layout { grid-template-columns: 1fr !important; } }`。  
   内联样式加载在 `base.css` **之后**且带 `!important` → **覆盖了 N-21 的 `minmax(0, 1fr) !important`**，  
   轨道退化成 `minmax(auto, 1fr)`，最小值取内容的 min-content（900px）→ blowout。  
   虽然两个 table 都被 `overflow-x:auto` 容器包裹，但 `min-width:auto` 让 blowout **绕过滚动容器一路传导到 `html`**。

**波及面**：全站共 **10 处** `grid-template-columns: 1fr !important`  
（`product_detail` / `product_series` / `project_detail` / `news` 的 `sidebar-layout`，`about.html` 5 处、`contact.html` 1 处）。

**修复（双保险，v1.1.12）**：

1. **根本解 `base.css`**：`.sidebar-layout > *, .about-story-grid > *, .contact-grid > * { min-width: 0; }`  
   —— 作用在 **grid item** 上，切断传导路径，**不依赖轨道写法，因此不会被任何内联 `!important` 反杀**。
2. **语义修正**：10 处内联 `1fr !important` 全部改为 `minmax(0, 1fr) !important`。
3. **表格自身适配**（用户要的是「重排」而非「不溢出」）：窄屏下 `.detail-energy-table th { white-space: normal }`（放开后自然换行，无需横向滚动）；9 列的 ordering 表保留横向滚动并加 `.scroll-hint` 滑动提示。

**验证**：修复后 rt400hb 移动端 `docScrollWidth` **921 → 390，溢出 0**；平板 768、桌面 1280 同样 0 溢出。  
**防回归**：`ResponsiveBlowoutAndHeroTests` 4 条断言（根本解存在 / 不存在裸 `1fr !important` / 4 个模板用 minmax / energy 表窄屏换行）。

> **教训（通用规则）**：修 grid blowout 时，**只改轨道不够**——轨道会被后加载的内联 `!important` 覆盖；  
> 而 `min-width:0` 加在 item 上不受影响。二者应同时做。

#### N-26 hero 竖版图与 `<picture>` 分档（2026-09-10，N-23 的根治，P1）

见 **§13**。要点：`picture` 是 **inline 元素**，包住 `.hero-slide` 后会在 track 内留下空行盒，  
必须配 `.hero-carousel-track > picture { display: contents; }`；且 `<source>` 命中后**不会回退到 `<img>`**，  
竖版文件缺失 = 手机端 hero **直接白屏**（比裁切严重），故加了文件存在性与比例的单元测试。

#### N-27 移动端底部按钮被遮——方向改判 v1.1.13（2026-09-10，P1）

- 抽屉 padding 用 `calc(32px + env(safe-area-inset-bottom))` 让出 34px

  **几乎都返回 0 或直接不支持 env() 函数**，按钮紧贴视口底被百度底部工具栏完全遮住。

- **viewport-fit=cover 反而有害**：会让桌面浏览器误判可视区，且把 iOS 的 Home Indicator 区域  
  暴露到 layout 区，把按钮往下推（不再"自带避让"）。

**v1.1.13 改判后的正解**：

- **撤销** `viewport-fit=cover`（不再依赖 env() 前置条件）
- `.panel-actions` 的 `padding-bottom` 改用 **`max()` 兜底**：
  ```css
  padding-bottom: max(80px, calc(env(safe-area-inset-bottom, 0px) + 48px));
  ```

  - 安卓（env=0 或不支持）：`max(80, 48)` = **80px 兜底**
  - 80px ≈ 安卓导航条(50) + 手势条(24)，任一设备都不会被遮

#### N-29 iOS / 安卓字体观感差异——真正根因（2026-09-10，v1.1.14，P1）

**用户报告**："iOS 与安卓访问看到的字体不一样，安卓系统看到的字体更好一点。"

**直觉归因**（错的）：iOS 字体没装好，或字体文件加载失败。

**真正根因**（探针脚本 `.workbuddy/tmp/probe_font.py` 抓到）：

```json
{ "body_ff": "\"Times New Roman\"",
  "root_ff_body": "&#x27" }
```

`:root` 里的 `--ff-body` CSS 变量**实际值是 HTML 实体 `&#x27`**，被 Django 模板 `{{ }}` 默认 HTML 转义产生——admin 存的 `'Inter'` 里的 `'` 全部转义成 `&#x27;`，整个 CSS 变量被破坏，浏览器 fallback 到 system-ui → 最后兜底到 Times New Roman。

**为什么"安卓字体更好"**：

- iOS Safari 自动 fallback 到 **SF Pro（英文）+ PingFang SC（中文）**——两套独立字体，baseline / x-height 不同 → 中英文混排时**视觉上"参差"**
- 安卓 Chrome 自动 fallback 到 **Roboto（英文）+ Noto Sans CJK（中文）**——Noto 家族设计上保持中英文字宽一致 → 看起来"整齐"
- 不是设备字体差异，是字体栈**完全缺中文 fallback**导致 OS 各自 fallback

**修复 4 处**：

1. **`templates/base.html` 模板行加 `|safe`**：`{{ config.font_family_body|safe }}` —— 让含 `'` 的 admin 字段正确输出
2. **`base.css` 字体栈补全**：加 `-apple-system, BlinkMacSystemFont, "PingFang SC", "Hiragino Sans GB", "Microsoft YaHei", "Source Han Sans CN", "Noto Sans CJK SC", Roboto`
3. **`pages/models.py` 默认值更新**：admin 即使不动配置，字体栈也含中文
4. **`pages/migrations/0024_update_siteconfig_font_chinese_fallback.py`**：data migration 把已存在的 SiteConfig 单例升级到新默认（保护管理员自定义：仅当值匹配"老默认值"集合才升级）

**修复后实测**：

```
body_ff: "Inter, -apple-system, BlinkMacSystemFont, system-ui, \"PingFang SC\",
         \"Hiragino Sans GB\", \"Microsoft YaHei\", \"Source Han Sans CN\",
         \"Noto Sans CJK SC\", Roboto, sans-serif"
```

**防回归**：新增 `test_admin_font_injection_uses_safe`（断言模板用 `|safe`）+  
`test_font_stack_has_chinese_fallback`（断言 base.css 含 `PingFang SC`/`Noto Sans CJK`/`-apple-system`）。

**教训（永久铭记）**：Django 模板 `{{ }}` 默认 HTML 转义，**任何 admin 注入 CSS 的字段都得加 `|safe`**，否则字面意义上的 `'Inter'` 会变成 `&#x27;Inter&#x27;` 整个破坏 CSS 变量。这种 bug 的特点是**不抛 TemplateSyntaxError、不进 check/test、不进日志，只在真实渲染时静默退化到兜底字体**，极难发现——只有探针脚本读 `getComputedStyle().getPropertyValue('--ff-body')` 才能抓到。

#### N-31 F7 断点统一漏网：8 处 `max-width: 768px` 与平板档边界重叠（2026-09-10，v1.1.19，P1）

**发现经过**：v1.4.2 阶段二复核时逐条验证 F7 成果。F7 的测试断言
`test_no_legacy_900px_breakpoint_in_source`（正则 `@media\s*\(\s*max-width:\s*900px\s*\)`）**通过**，
900px → 767px 的改造确实彻底。但**该断言只守 900px，匹配不到 768px**，于是遗漏了下面这一类。

**现状**：源码中仍残留 **8 处 `@media (max-width: 768px)`**：

| 文件 | 行号 |
|---|---|
| `static/css/base.css` | 316、1979、2000、2055、2091、2100 |
| `templates/about.html` | 284 |
| `templates/contact.html` | 171 |

> 注：`base.css` 另有 2 处 `max-width: 900px`（约 767、1997 行）是**元素限宽**
> （`.hero-content` / `.about-story-stats` 的 `max-width`），不是媒体查询，**不是问题**，勿误改。

**问题本质**：F7 确立的三档是 `≤767 / 768–1199 / ≥1200`，平板档起点是 `min-width: 768px`
（base.css 中有 20+ 处）。而 `max-width: 768px` 在 **768px 这个点上会与平板档同时命中**：

```
断点轴：  ────────────┊───────────────────────┊──────────
                   767px                  1199px
手机档 (max-width:767) 平板档 (min-width:768)
漏网的 (max-width:768) ──┊── 在 768 这个点与平板档重叠
                         ↑
                    iPad 竖屏 = 768pt，正好落在这一点
```

CSS 媒体查询在同优先级下**后定义者胜出**，因此 768px 处的实际表现取决于源码书写顺序——
这正是「断点统一」想要消除的那一类不确定性。

**影响面**：iPad 竖屏（768×1024）、iPad mini、部分安卓平板竖屏。属于「不一定出错，但行为不可预测」。

**修复方案**：
1. 8 处 `max-width: 768px` → `max-width: 767px`（与 F7 手机档定义一致）
2. 补一条测试断言：源码中不得出现 `@media (max-width: 768px)`，只能出现 `767px`
   （与现有 900px 断言同构，正则 `@media\s*\(\s*max-width:\s*768px\s*\)`）
3. `scripts/e2e/run_checks.py` 在 **768px 视口**跑一次，确认改后无回归
   （现有视口档为 320/390/768/820/1280/1440 —— 768 已在列，正好覆盖该边界）

**状态**：✅ **已修复（2026-09-10，v1.1.20 / v1.4.2）**。同一问题在 `docs/优化建议清单.md` 记为 **N-29**，两份文档同步关闭。

**实际实施**（与上面「修复方案」的两点差异）：

1. **8 处全部改为 `767px`**（base.css 6 处 + about.html + contact.html）。改后全源码断点收敛为：

#### N-19 L2 横向溢出断言基准失效（v1.1.6 复核发现）

`scripts/e2e/run_checks.py` 用 `document.documentElement.scrollWidth - window.innerWidth <= 1` 判溢出。  
但 `is_mobile=True` 的移动端模拟下，**内容过宽会把 layout viewport 一起撑大**（实测：设定 320 档 → `window.innerWidth` 报 **364**），于是 `scrollWidth - innerWidth` 恒为 0 —— **溢出被自我掩盖，断言永远绿**。

→ 按此修正后，320 档 `/projects/` 应当如实报出约 44px 溢出（内容最小宽度 ≈364px），这正是当前被隐藏的真实问题。

#### N-20 L2 的 N-1 检查把 `type="hidden"` 计入 → 误报（v1.1.6 复核发现）

→ **修复：选择器排除 `type="hidden"`**（现有代码只排除了 honeypot `tabindex="-1"`，不够）：

```javascript
Array.from(document.querySelectorAll('#contactForm input, #contactForm textarea'))
  .filter(el => el.type !== 'hidden' && el.getAttribute('tabindex') !== '-1')
```

### 6.2 L1 后端断言（零新依赖，必跑）

def test_mobile_nav_contract(self):

def test_mobile_nav_hidden_rule_present(self):

        r'@media[^{]*max-width:\s*767px[^{]*\{[^@]*?\.nav-links\s*\{[^}]*display:\s*none'

- 断言 `collectstatic` 产物与源一致（可选）：`manage.py collectstatic --noinput` 后比对 `staticfiles/css/base.css` 含新增规则。

### 6.6 与部署流程的衔接

```text
本地全绿（L1 + L2 + L3 全绿，其中 L2 跑本地 runserver 视口模拟）
  → 生产 URL 只读跑一遍 L2（防 DEBUG / 压缩 / 数据差异，见 §6.8.2）
  → 提交（该阶段一次性提交，含 F6 的 ?v= bump）
  → 推送到 Vercel Preview（预览分支）
  → 在预览环境用同一 §4 清单抽验（重点：collectstatic 产物、Whitenoise 缓存、?v= 版本号是否生效）
  → 确认无误 → 合并/发布生产（并打 git 标签）
```

- **每阶段只推送一次**（该阶段全部通过后），避免半成品上线。
- **部署后再跑一次 L1**（`manage.py test`，生产环境同样本）与 L3 核心页抽验；若发现回归，**立即回滚到上一发布版本（git 标签）**，回到对应阶段修复后再走上述流程。

### 6.8 还需要真机 / 部署后验证吗？—— L2 的能力边界

> **结论**：L2 **可替代约 80% 的部署后真机验证，且不需要部署**——本地 `runserver` + Playwright 视口模拟即可完成。但**不能 100% 替代**；真机应保留为"发布前一次性确认"，而不是每次改动的回归手段。

#### 6.8.1 本地直连：不部署、不用手机

```powershell
python manage.py runserver 0.0.0.0:8000
```

Playwright 访问 `http://127.0.0.1:8000`，并在 context 上设置：

```python
ctx = browser.new_context(
    viewport={"width": 390, "height": 844},
    device_scale_factor=3,
    is_mobile=True,      # 关键：启用移动端视口模拟
    has_touch=True,      # 关键：启用触摸事件
)
```

`is_mobile=True` 会让 Chromium **真正按移动端渲染**：`meta viewport` 生效、媒体查询按 390px 计算、`@media (hover: none)` / `(pointer: coarse)` 生效。

> ⚠️ 这与"把桌面浏览器窗口拉窄到 390px"**有本质区别**：拉窄窗口不改变 `is_mobile`，`meta viewport` 不生效、`:hover` 仍按桌面处理。手拉窗口测出来的"没问题"是假象——这正是 P0-1 一直没被发现的原因之一。

#### 6.8.2 但本地 ≠ 生产，这四个差异必须处理

| 差异           | 影响                                 | 处理                                                                |
| ------------ | ---------------------------------- | ----------------------------------------------------------------- |
| `DEBUG=True` | 静态文件直出未压缩、错误页不同、`ALLOWED_HOSTS` 宽松 | 合入前用 `DEBUG=False` + `collectstatic` 本地跑一次                        |
| 无压缩 / 无 CDN  | 加载性能与字体阻塞体感不一致                     | **性能类结论一律以生产为准**                                                  |
| 本地 0 延迟      | 掩盖慢网下的布局跳动（CLS）                    | 需要时用 CDP 限速：`cdp.send("Network.emulateNetworkConditions", {...})` |
| 本地 seed 数据   | 与线上文案长度不同，影响换行与截断                  | 关键页用生产 URL 复验                                                     |

**推荐折中**：Playwright **直接指向已部署的生产 URL 做只读回归**（只发 GET、不写库、不改数据，零风险）。既真实，又省掉本地搭生产环境的麻烦。

#### 6.8.3 L2 能覆盖什么 / 不能覆盖什么

**✅ 能覆盖（本方案全部 P0 与大部分 P1 都在此列）**

| 能力                                       | 断言方式                                                          |
| ---------------------------------------- | ------------------------------------------------------------- |
| 横向溢出 / 元素被裁切（P0-1）                       | `scrollWidth > innerWidth`；`boundingBox` 越界检查                 |
| 断点是否生效（F1' nav-links 隐藏、F3' 面板含 Contact） | 可见性 + 面板内链接文本集合                                               |
| 汉堡是否被挤出（P0-1 伴生）                         | `boundingBox.right ≤ viewport width` 且可点击                     |
| 实际渲染字号、触摸目标尺寸                            | `getComputedStyle` / `getBoundingClientRect`                  |
| 侧栏默认收起 + 展开收起交互（F4'）                     | 点击后断言高度/可见性变化                                                 |
| RTL（`/ar/`）溢出与方向                         | `dir` 属性 + 溢出断言                                               |
| `prefers-reduced-motion`、深色模式            | Playwright 原生：`reduced_motion="reduce"`、`color_scheme="dark"` |
| 三档视口截图基线                                 | 截图 + 像素 diff，可无限重跑                                            |

**❌ 不能覆盖（约 20%）—— 及各自的替代验证手段**

| 项目                                | 为什么模拟不了                                                             | 替代手段                                                                                       |
| --------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **iOS 输入框聚焦自动放大（N-1）**            | 这是 Safari/iOS 的 **UI 层行为**；Windows 上即使装了 Playwright 的 WebKit 也不保证复现 | **静态断言**：断言所有 `input/textarea/select` 的 computed `font-size ≥ 16px`。Chromium 上就能跑，且比真机更可回归 |
| `env(safe-area-inset-*)`（N-6）     | 桌面浏览器下恒为 0                                                          | **静态断言**：断言 Cookie 横幅 CSS 含 `env(safe-area-inset-bottom)` 且带非 0 fallback                   |
| `100vh` 与 iOS 地址栏收缩（N-11）         | 依赖 Safari 动态视口                                                      | 代码已用 `100dvh` + `100vh` 降级（`base.css:407-408`），断言二者**成对出现**即可                              |
| 真实触摸/手势：双击缩放、长按菜单、`:hover` 粘滞     | 只能派发合成事件                                                            | 真机点一遍（约 1 分钟）                                                                              |
| 真实性能：手机 CPU 下 555KB hero 图 + 阻塞字体 | 本地桌面 CPU + 0 延迟完全掩盖                                                 | 生产 URL + Lighthouse / PageSpeed **移动端档**                                                   |

## 8. 更优替代方案

### 8.1 导航：单一数据源 + 移动端"功能不减"

**核心思路：不要靠"隐藏"来腾空间，而是把功能搬进抽屉。**

```html

<a href="{% url 'home' %}">{% trans "Home" %}</a>
<a href="{% url 'products' %}">{% trans "Products" %}</a>
<a href="{% url 'projects' %}">{% trans "Projects" %}</a>
<a href="{% url 'news' %}">{% trans "News" %}</a>
<a href="{% url 'about' %}">{% trans "About" %}</a>
<a href="{% url 'contact' %}" class="nav-only-mobile">{% trans "Contact Us" %}</a>
```

- 桌面 `.nav-links` 与移动面板**共用**该片段 → 永远不会再出现"面板少一项"。
- `.nav-only-mobile` 在 `≥768px` 时 `display:none`（桌面已有独立 `.nav-cta`）。
- 移动面板底部追加 **语言切换 + 主题切换**。
- 移动端导航条只剩 **logo + 汉堡**（≈200px），**物理上不可能溢出**。

> 收益：一次改动同时解决 P0-1、P0-2、N-2、N-3，且不丢失任何功能。

### 8.2 侧栏折叠：checkbox hack（替代 `<details>`）

```html
<input type="checkbox" id="sidebarToggle" class="sidebar-toggle-input">
<label for="sidebarToggle" class="sidebar-toggle-label">筛选 / 目录</label>
<div class="sidebar-nav"> ...分类树... </div>
```

```css
.sidebar-toggle-input, .sidebar-toggle-label { display: none; }        /* 桌面：常驻展开 */
@media (max-width: 900px) {
  .sidebar-toggle-label { display: flex; }                              /* 移动端：显示折叠按钮 */
  .sidebar-toggle-input:not(:checked) ~ .sidebar-nav { display: none; } /* 默认收起 */
}
```

**关键原则：把"展开"作为 HTML 默认态，"收起"作为增强态。** 反过来做（默认收起、靠 JS 展开）会让无 JS 用户永久失去分类导航。  
备选（渐进增强）：HTML 不写 `hidden`，由 JS 在 `matchMedia('(max-width:900px)')` 命中时主动收起 —— 无 JS 时侧栏始终展开，退化为当前行为，不会变成"内容不可达"。

### 8.3 字号：`min/max` 替代 `clamp`，并限定在移动端作用域

```css
/* base.html 注入时保留原始值，命名 -admin */
:root { --fs-hero-title-admin: 3.5rem; --fs-section-title-admin: 2.25rem; }

/* base.css：仅移动端收口，桌面渲染路径零改动 */
@media (max-width: 767px) {
  :root {
    --fs-hero-title:    min(var(--fs-hero-title-admin),    max(30px, calc(1rem + 4vw)));
    --fs-section-title: min(var(--fs-section-title-admin), max(22px, calc(0.85rem + 2.4vw)));
  }
}
```

| 场景                 | 原 `clamp(30px, 7vw, 56px)` | 新 `min(56px, max(30px, 1rem+4vw))` |
| ------------------ | -------------------------- | ---------------------------------- |
| 390px，后台值 56px     | 30px                       | 31.6px                             |
| 768px，后台值 56px     | 53.8px                     | 46.7px                             |
| 1280px，后台值 56px    | 56px                       | 56px                               |
| **390px，后台值 24px** | **30px（与意图相反）**            | **24px（尊重后台）**                     |
| 用户放大浏览器字号          | 不响应                        | 响应（含 rem 基线）                       |

### 8.4 验收：用本机 Edge 做零安装 L2

| 方案                                           | 安装成本                                | 可做断言             | 推荐度    |
| -------------------------------------------- | ----------------------------------- | ---------------- | ------ |
| **L2-lite：`msedge --headless --screenshot`** | **零**（系统自带）                         | 仅截图              | 立刻可用   |
| **Playwright + `channel="msedge"`**          | `pip install playwright`，**不下载浏览器** | 完整（可见性/点击/无横向滚动） | **推荐** |
| L3 纯人工 DevTools 逐档切                          | 零                                   | 不可回归、易漏          | 仅作补充   |

最小可用用例（约 30 行，覆盖 P0 全部）：

```python
from playwright.sync_api import sync_playwright
PAGES = ["/", "/products/", "/projects/", "/news/", "/about/", "/contact/"]
SIZES = [(320,568),(390,844),(768,1024),(1024,768),(1440,900)]
with sync_playwright() as p:
    b = p.chromium.launch(channel="msedge")
    for w, h in SIZES:
        pg = b.new_page(viewport={"width": w, "height": h})
        for url in PAGES:
            pg.goto("http://127.0.0.1:8000" + url)
            assert pg.evaluate("document.documentElement.scrollWidth <= window.innerWidth + 1")
            if w < 768:
                assert pg.locator("#hamburgerBtn").is_visible()
                box = pg.locator("#hamburgerBtn").bounding_box()
                assert box and box["x"] + box["width"] <= w
                assert not pg.locator(".nav-links").is_visible()
            pg.screenshot(path=f"shots/{w}-{url.strip('/') or 'home'}.png")
```

## 13. Hero 竖版图规格与 `<picture>` 分档（2026-09-10，v1.1.12，N-23 根治）

> 本节回答「竖版 hero 图**分辨率和比例多少合适**」并给出已落地的实现。  
> 模板注释里引用的 §13 即本节。

### 13.1 为什么必须出竖版（先理解约束，再谈尺寸）

移动端 `.hero-bg` 的实际盒子（N-23 实测，iPhone 14 / 390×844）：

| 项                                | 数值                    |
| -------------------------------- | --------------------- |
| 视口                               | 390 × 844 pt          |
| `.hero` 高                        | ≈ 810 px              |
| `.hero-bg` 图带高（62%，v1.1.11 缓解方案） | ≈ **502 px**          |
| 图带**宽高比**                        | 390 ÷ 502 ≈ **0.777** |

而现有横版图是 **16:9 = 1.778**。把 1.778 的图 `object-fit:cover` 塞进 0.777 的盒子：  
图片被放大到 1440px 渲染宽，**横向只能露出约 27%**（这就是「hero 图被裁切」的量化来源）。

→ **结论：竖版图的宽高比要接近 0.777**，裁切才会消失。

### 13.2 推荐规格（直接照此出图）

| 档位        | 触发条件               | 文件名                                  | 尺寸（宽×高）         | 比例        | 目标体积     | 状态      |
| --------- | ------------------ | ------------------------------------ | --------------- | --------- | -------- | ------- |
| **竖版 2x** | 视口 ≤ 767px         | `hero-main-{1,2,3}-portrait.webp`    | **1170 × 1560** | 3:4（0.75） | ≤ 200 KB | 建议终版    |
| 竖版 1x（可选） | 视口 ≤ 767px 且 DPR=1 | `hero-main-{1,2,3}-portrait@1x.webp` | 780 × 1040      | 3:4       | ≤ 110 KB | 省流量，非必需 |
| 横版（现有）    | 视口 ≥ 768px         | `hero-main-{1,2,3}.webp`             | 1920 × 1080     | 16:9      | —        | 已存在     |

**为什么是 3:4 / 1170×1560：**

- **比例**：容器 0.777，3:4 = 0.750 → 以宽度为准铺满后只裁掉约 **18px 高度**（< 2%），视觉上等于零裁切。  
  9:16（0.5625）**不要选**——比容器窄太多，会被上下大量裁切，等于白做。
- **宽度 1170**：390pt × 3（iPhone 14 Pro 的 DPR=3）= 1170，**正好覆盖 3x 屏的物理像素**。
- **高度 1560**：1170 ÷ 0.75 = 1560。
- 若嫌 3x 太重，**810×1080 即可满足 2x**（810 ÷ 390 ≈ 2.08x），当前仓库里的版本就是这个规格。

**格式与压缩**：WebP，`quality=82, method=6`。RGB 模式（无 alpha 可再省 10~15%）。  
若需兼容极老浏览器，图片本身 WebP 已覆盖 97%+，`<picture>` 里**不需要**额外出 JPG。

### 13.3 构图安全区（比尺寸更容易被忽略，却直接决定成败）

```
┌─────────────────────┐ 0%    ← 顶部 0–12%：保持暗部/简洁
│   ▓▓▓ 暗部 ▓▓▓      │       （hero-meta 小字压在这里，需对比度）
├─────────────────────┤ 12%
│                     │
│   ★ 主体放这里 ★    │ 12%–55%  ← 垂直安全区
│   （水平中央 70%）  │
│                     │
├─────────────────────┤ 55%
│                     │
│   渐隐区（mask）    │ 55%–100% ← 会被渐变淡出，
│   别放关键细节      │            放天空/看台/留白
└─────────────────────┘ 100%
```

- **垂直**：主体落在 **12%–55%**；`.hero-slide` 的 `object-position: center 42%` 正是取这一段。
- **水平**：主体收在**中央 70%** 内，左右各留 15% 余量（`cover` 在更窄的盒子上会裁两边）。
- **顶部 12%**：压着 `.hero-meta` 文字，需要暗部或低细节，否则文字不可读。
- **底部 45%**：`mask-image` 渐隐区（v1.1.11 的 N-23 缓解方案）。**若你希望竖版占满整屏**，  
  可移除该缓解（`.hero-bg{height:100%}` + 去掉 mask），此时底部约束解除、但要注意与 hero 文案的对比度。

### 13.4 已落地的实现

**`templates/home.html`**（三张图同构，仅编号不同）：

```html
<picture>
  <source media="(max-width: 767px)"
          srcset="{% static 'images/hero-main-1-portrait.webp' %}"
          type="image/webp">
  <img src="{% static 'images/hero-main-1.webp' %}"
       alt="LED sports stadium lighting"
       class="hero-slide active" fetchpriority="high" decoding="async">
</picture>
```

**`static/css/base.css`**：

```css
.hero-carousel-track > picture { display: contents; }
```

**四个实现要点（都是坑）：**

1. `picture` 是 **inline 元素**，包住 `.hero-slide` 后会在 track 内留下空行盒 → 必须 `display: contents`。
2. `<source>` 一旦 `media` 命中就**不会回退**到 `<img>` —— 竖版文件 404 = **手机端 hero 直接白屏**，  
   比裁切严重得多。故加了文件存在性与「高 > 宽」的单元测试（`test_hero_portrait_files_exist`）。
3. 首图**不能**加 `loading="lazy"`（它是 LCP 图片），并加 `fetchpriority="high"`；第 2/3 张保持 `lazy`。
4. 不再写 `width`/`height` 属性：`.hero-slide` 是 `position:absolute; inset:0`，尺寸完全由 CSS 决定，  
   写死横版的 `1920×1080` 反而给浏览器错误的宽高比提示。

**当前仓库状态**：已用现有横版**零上采样**裁出 810×1080 竖版三张（73 / 118 / 98 KB），  
保证上线即有图、不白屏。**用你自己拍的竖版原图覆盖同名文件即可，无需改任何代码。**

### 13.5 替换图片的完整步骤

1. 按 §13.2 / §13.3 出图（3:4，1170×1560，WebP q82）。
2. 覆盖 `static/images/hero-main-{1,2,3}-portrait.webp`（**保持同名**）。
3. `templates/base.html` 的 CSS 版本号 `?v=N` **+1**（否则 CDN/浏览器用旧缓存）。
4. 跑 `python scripts/e2e/visual_review.py --paths / --widths 390` 看截图确认。

### 15.5 真机复核修正记录：F8 detail-specs 移动端 1 列 → 2 列（2026-09-10，v1.1.24 / v1.4.6）

**触发**：用户真机复核 `rt410-series` 页面截图（iPhone 竖屏 390×844）—— 主要参数区（260W POWER / 125lm/W EFFICACY / 32500+lm OUTPUT / 18~100° BEAM ANGLE 共 4 项）排成 1 列 4 行，与桌面端 2 列不一致，用户要求「应与 PC 端一样排成纵向两列，最多两列三行」。

**修正内容**（product_detail.html:866-880）：

```css
/* F8 修正：移动端恢复 2 列（与桌面端一致，4 项 2x2、6 项 2x3，最多 3 行），
   字号与 gap 同步收敛，避免在 390px 视口下拥挤或换行。 */
.detail-specs {
  grid-template-columns: repeat(2, 1fr);
  gap: 12px 16px;
}
.detail-spec-value { font-size: 1.1rem; }  /* 桌面 1.35rem → 1.1rem */
.detail-spec-label { font-size: 0.7rem; }  /* 桌面 0.8rem  → 0.7rem */
```

**L1 守卫**（pages/tests.py `ResponsivePhase2Tests.test_detail_specs_two_columns_on_mobile`）：
- 旧断言 `assertIn('grid-template-columns: 1fr', block)` → **改名 + 反向断言**：
  - 必须含 `repeat(2, 1fr)`（强制 2 列）；
  - 摘除 `repeat(2, 1fr)` 后不得出现 `grid-template-columns: 1fr`（防止再退化）。
